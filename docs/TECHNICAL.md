# Technical overview

This document describes how the port is built. It contains no game data; addresses and names mentioned are locations and symbols in the original Saturn programs (the main
program `0RALLY.DAT`, loaded at 0x06004000, and the 68000 sound driver), given so that the tools and the other documents can be followed with a disassembler of your own copy.

## The idea

The Saturn game is two 28.6 MHz SH-2s feeding VDP1 (textured quads) and VDP2 (backgrounds) at 30 fps. The PSP is much faster than that, so the port reimplements the game
instead of emulating it, and keeps the original program only as a **reference**:

1. **The game logic is written again in C** (`src/`), subsystem by subsystem, by reading the original (the disc even carries the linker's debug file `RALLY.DBG`: 2,476 symbols and the
   module layout, see `tools/dbg_parse.py`).
2. **The original runs in a small SH-2 interpreter** (`tools/sh2.py`, `tools/saturn_env.py`: the oracle) on the data of your disc. Every C subsystem is checked against it: the same
   inputs go into both and the memory / draw lists / sound calls that come out must be identical.
3. **The menu screens are exact ports** that run on a model of the Saturn's memory (`src/sat*.c`): the screen code is ported function by function, keeps the original's addresses, and is compared
   with the oracle after every V-blank tick (`docs/menu_port_guide.md`).
4. **Sound**: the original's 68000 driver runs on an interpreter and a model of the SCSP mixes it (`src/m68k.c`, `scsp.c`, `snd.c`); the SH-2 side of the sound library is ported function by function
   (`snd_lib.c`) and the race's sound events are generated by `sndev.c` (checked against the oracle's sound calls).

## Pipeline

`python tools/make_data.py CUE` runs these steps (`--list` shows them), `bash tools/build.sh` then builds the EBOOT and stages the game folder:

```
Sega Rally Championship (USA).cue / .bin
   |  extract_disc.py          ISO9660 files + system area + the CD tracks as WAV                       -> extracted/disc, extracted/audio
   |  dbg_parse.py             RALLY.DBG (linker debug file): module layout, symbols                    -> extracted/analysis/symbols.tsv
   |  ghidra_import.py         function boundaries of 0RALLY.DAT (Ghidra headless, SH-2)               -> extracted/analysis/functions.tsv
   |  conv_phys.py             physics / race-flow tables                                              -> course/phys.dat
   |  conv_track.py            collision grid, block / slice data                                      -> course/*.rct
   |  conv_parts.py            course models as lists of parts, textures, visibility lists             -> course/*.rcp
   |  conv_bg.py               VDP2 sky panoramas (the original's VDP2 set-up code runs in the oracle) -> course/*.rbg
   |  conv_objects.py          OBJECT.MAD / ANIMAL2: cars, signs, people, animals                      -> course/object.rcp
   |  conv_cars.py, conv_events.py, conv_hud.py, oracle.py hudinit, conv_hudend.py                      -> course/cars.dat, events.dat, hud*.dat
   |  conv_menu.py             every file the menus load, as the console's memory has it (BPE expanded) -> menu/*.blk, *.raw
   |  conv_select.py, conv_ending.py, conv_endcar.py, conv_alpha.py   3D parts of the menu screens      -> course/*.rcp
   |  conv_pspad.py            (optional) your own PSP picture for the KEY CONFIG page                  -> menu/psp_pad.bin
   |  conv_cdda.py             the CD tracks as MP3 (speaker-friendly)                                  -> cd/*.mp3
   |  conv_bgm.sh              the menu songs rendered with the original driver (bgm_render.c)         -> snd/*.bgm
   v
tools/build.sh  (psp-cmake)    EBOOT.PBP + data/                                                       -> dist/SegaRallyPSP/
```

Data formats are described in the converters' headers (`RCP1` parts, `RCT1` collision, `RBG1` sky, `MBK1` memory images, `PHY1` tables ...) and in `docs/render_pipeline.md`,
`docs/collision_world_ai.md`, `docs/physics.md`.

## The engine (`src/`)

| File | |
|---|---|
| `main.c` | PSP start-up; the first frame viewer (kept for the data checks) |
| `drive.c`, `camera.c`, `pmap.c`, `coli.c`, `gmath.h`, `fx.h` | the driving core: `execCar` and everything it calls (physics, collisions, race flow, laps, clock, goal, game over), the camera, the visible-part list, the collision map |
| `opp.c`, `oppmath.h` | the other cars: spawn, AI along the guide line, four levels of detail, car-car collisions, rank |
| `event.c` | the scenery objects (spectators, gates, flags, animals, the start line) and the desert's helicopter |
| `car.c`, `spray.c`, `render.c`, `hud.c`, `hudgen.c` | car display, spray / dust, the painter's-algorithm renderer for the game's polygons (GE), the HUD (VDP2 text layers redrawn) and its name-table generators |
| `play.c` | the race loop: input, `drive_move`, the camera, the display, the sounds, the pause menu, replays, hand-over back to the menus |
| `sat*.c`, `satmenu.c`, `satlib.c`, `sat_boot.c`, `sat_save.c` | the Saturn memory model, boot, V-blank handlers, the library routines (scroll, windows, pad), backup RAM saves |
| `menu_*.c` | one file per screen group, ported exactly: mode select, arcade chain, time attack, set-up, options, records, name entry, ranking, results, photo (staff roll), ceremony and ending, title / intro |
| `menu_host.c`, `menu_pspfix.c`, `menu_padcfg.c`, `vdpr.c` | the PSP host of the menus: pacing, pad, software VDP1 / VDP2 renderer, 3D objects of the screens, the Saturn button pictures redrawn as PSP buttons |
| `ending_engine.c` | the ending's replay: the race engine run from the recorded inputs |
| `m68k.c`, `scsp.c`, `snd.c`, `snd_lib.c`, `sndev.c`, `snd_psp.c` | the sound system (see above); `bgm.c` plays pre-rendered menu songs; `cdda.c` the MP3 tracks; `sndlog.c` an optional timing log |
| `devauto*.c`, `perf.c` | development aids: unattended test runs (script file `data/autoplay.txt`), timing logs |

## Verification with the original code

| Tool | What it checks |
|---|---|
| `tools/oracle.py`, `saturn_env.py`, `sh2.py` | run the original's race code: `oracle.py run --course N --scenario S --slots ...` writes the car state after every pass; `oracle_*.sh` make the full set of traces (all stages, arcade / practice / time attack, other cars, ghost, replay, ending, HUD, sound calls) |
| `tools/test_drive.sh`, `test_drive_all.sh` | `src/drive.c`, `camera.c`, `pmap.c`, `hudgen.c`, `opp.c`, `sndev.c` against every trace: the whole 0x600-byte car slot after every pass, the other cars' slots, the part list, the HUD name tables, the end-of-race screens |
| `tools/refframe.py`, `vdp1.py`, `vdp2.py`, `check_frames.ps1`, `compare_frames.py` | pictures: the original's polygon pipeline into a software VDP1 versus the PSP renderer |
| `tools/test_event.sh`, `test_gmath.sh`, `test_spray.sh`, `test_opp.sh`, `test_pause.sh`, `test_hudend.sh`, `test_hudinit.sh`, `test_snd_ev.sh`, `test_save.sh` | the smaller subsystems against recorded vectors |
| `tools/menu_oracle.py`, `scn_*.py`, `test_menu.sh`, `test_menu_fast.sh` | the menu screens: scenarios press buttons on the original and record memory after every tick; the C port must produce the same (`tools/menu_scenarios.txt`, 158 scenarios) |
| `tools/m68k_fuzz*.py`, `test_m68k.c`, `bgm_render.c`, `test_snd.c` | the 68000 interpreter against `unicorn`, the sound driver with and without the C shortcuts (identical output) |

All traces are written to `extracted/oracle/` (git-ignored). Recording them takes a long time (`oracle_all.sh` about 15 minutes; `oracle_m6/m7/ta/ghost/replay/hudend/snd.sh` and the
menu scenarios hours, partly parallel); the host tests then run in seconds to minutes. A typical session from the project root (inside WSL / Linux, Python with the disc data converted):

```bash
bash tools/oracle_all.sh && bash tools/oracle_m6.sh && bash tools/oracle_m7.sh && bash tools/oracle_ta.sh   # record
bash tools/test_drive_all.sh                                                                                 # every trace against the C port
python tools/menu_oracle.py title_start                                                                      # one menu scenario (see tools/menu_scenarios.txt)
bash tools/test_menu_fast.sh title_start                                                                      # ... checked against the C port
```

Result at the time of the release: `test_drive_all.sh` 141 traces, 0 differing passes in every one; `test_menu_fast.sh` 158 scenarios, 0 failed.

## Conventions and pitfalls

* All converters write below `extracted/`; `tools/build.sh` copies `extracted/psp/` into the game folder as `data/`.
* The game's data is big-endian; the PSP is little-endian. The C code reads original tables by their original addresses through helpers (`g16` / `g32` ...); keep that when adding code.
* Run the tools with the project root as the working directory. On Windows the host tests and `tools/build.sh` run in WSL; call WSL from PowerShell, not Git Bash (it rewrites `/mnt/...` paths).
* PPSSPP's virtual time is optimistic for the CPU and does not show every audio problem of the real PSP (the CD music never started there for a long time: `sceUtilityLoadAvModule` fails on the real
  firmware, `sceUtilityLoadModule` works; and the memory stick stalls for tens of milliseconds): for sound and speed use the real PSP. `data/sndlog` (an empty file) writes an audio timing log (`docs/sound.md` 6).
* Do not read data that another processor writes (the MP3 decoder's output) with the CPU without invalidating the data cache, and do not change what the audio hardware gets without a test on a real PSP.
* Unattended runs in PPSSPP: `tools/autorun.ps1` with a script file (`docs/menus.md` section 20).

## Not ported

* The 2 Player Battle (`cs_battle_2p`, the split-screen race, the VS rules `vs_rank_calc` / `vs_g_ctrl`, the 2P models, the P2 sound driver): `docs/twoplayer.md`.
* The practice mode's secret ghost car and the pause box's hide combination (X + Y + Z of the Saturn pad), the new-best-lap jingle and the beep of the last seconds of the clock.
