# Porting a menu screen (M8): the method, the tools, the pitfalls

Decision (user, 2026-10-20): **every menu screen is ported exactly from the original code and checked against the original running in the oracle.**  Text that names Saturn controller buttons is changed to the PSP's later (the converter patches the pictures; see section 8).
Rules that stay in force: nothing derived from the game / console is committed (only code and tools); the game logic is ported to C **by hand**; the original `0RALLY.DAT` code is only the oracle; do not widen the scope of what the user approved.

## 1. How the port is built

* `src/sat.h/.c` = the Saturn memory model.  High work RAM (0x06000000), low work RAM (0x00200000), VDP1 / VDP2 VRAM, colour RAM, VDP2 registers are byte arrays addressed with the console's addresses and the big-endian accessors `R8/R16/R32/RS8/RS16/RS32/W8/W16/W32`.  SCU DMA (stores to 0x25FE0010/30/50) runs at once.  The ported code keeps **the original's data layout** (every global lives at its original address), so a screen can be compared byte for byte with the original.
* `sat_tick()` (= one V-IN + one V-OUT handler = the original's "recipes", `src/sat.c`) is called by the sync loops: `sync_vin/vout/dsp`, `sync_n(n)`, `intm_sync(n)`, `ints_sync()` all run **at least one tick before every test of their wait loop** (the oracle takes the V-blank at the loop heads).  A screen is a **blocking function** like the original: `slt_mode_main()` loops calling `intm_sync(46)`.  The host (PSP: draw the frame, wait for the V-blank, read the pad; test: compare with the oracle) hangs on `sat_host_tick`; the pad word for the next tick is `sat_pad`.
* Screen vectors: `[0x060A001C]` = main vector (the screen's main function), `[0x060A8800]` = the screen's own state handler.  They hold **original code addresses**.  A ported function is registered with `menu_reg(0x06022B5C, slt_mode_main)` (in `menu_<screen>_register()`, called from `menu_init()` in `src/satmenu.c`); `menu_call(addr)` runs it.  An address without a port aborts with `menu: no port for ...` (that is how an unported next screen shows up).
* Data tables of the program (jump tables, cursor tables, strings, picture tables) are read at their original addresses from memory: `tools/conv_menu.py` writes the data between the functions of `0RALLY.DAT` to `extracted/psp/menu/ROM.blk`, and every scatter-load file the menus use to `<NAME>.blk`.  Load a file the way the original does: `sat_load_file("MD_SLT0.DAT")`, `sat_load_name_at(addr)` (name string in memory), `sat_cd_request(req)` (CD request block).  Add files to `FILES` in `tools/conv_menu.py` when a screen needs one.
* Not ported on purpose (their memory is in the ignore list of `tools/test_menu.c`, each entry says why): the SMPC / CD-block / BIOS libraries (0x06035FAC ..), the sound driver (`snd_call(addr, r4, r5, r6)` logs the call exactly like the oracle's stub: M9 plays them), the polygon pipeline (mkpoly / matrix / zsort: the 3D parts are drawn by the PSP renderer; `draw_sprite` and `setup_texture` ARE ported because they write the VDP1 command table / textures that are compared).

## 2. Reading the original: the tools

* `python tools/lift.py <function|addr> --c` : the function as explicit C-like statements (registers `r0..r14` are variables, memory accesses are `RS16(0x060A88A4)`, `W16(...)`, calls are `name();  /* r4=..., r8=... */` = **the register arguments of that call**).  Read the call comment: the original passes arguments in r4..r9 **and in r1..r3, r8..r14 (global-like registers)**.  `python tools/lift.py <lo> <hi> --c` lifts an address range.  `extracted/liftc/<module>.c` has every module lifted (`python tools/gen_liftc.py`).
* `python tools/sh2dis.py <lo> <hi>` : the raw disassembly.  **Cross-check the raw code whenever the lift looks odd**: delay slots (an instruction after `bra/jsr/bt/s` runs *before* the branch takes effect, and `mov #imm,rN` there is NOT conditional), constants loaded before a branch, `.word` junk = data (jump tables / tables inside the code range are data: read them from memory by address).  The lifter flags `// !!! FALLS THROUGH` (the function table of Ghidra cuts some functions: e.g. `init_gspr` runs on into `init_nscr_vol`).  Ghidra's decompiler (`tools/rd.py`) has **wrong constants (`K(...)`), never port from it**.
* `python tools/needs.py <function> ...` : the functions still to port in the closure of a screen (direct calls + handler addresses stored into the vectors), excluding stubs (`tools/ported.txt`, hand kept) and everything already ported (a function counts as ported when its definition line carries a comment with the original address: `void fn(void)   /* 0x06022894 */`).  `python tools/cg.py`, `python tools/rd.py -s <addr>` (who refers to an address) help too.
* Register-argument conventions you will meet: `r8`/`r9` = src/dst of the copy routines; `r14` = a table pointer that **runs through consecutive tables** (`cd_map_set2` returns the advanced pointer); `r13` = base added to table addresses (`0xFDA44000` turns the table's 0x02800000 addresses into the LWRAM 0x00244000 where the file's data block was loaded); the `GBR` register as a base pointer.

## 3. The oracle and the test

* `tools/menu_env.py` runs the original headless (boot, V-blank handlers at the loop heads, pad words from the harness, file loaders as scatter-load, sound stubs).  `tools/menu_drive.py` (`Drv`): `d.run(n, pad)`, `d.tap(BUTTON)`, `d.until(cond)`, `d.watch(n)`, `d.shot(name)` (a PNG of the VDP2 layers), buttons `START A B C UP DOWN LEFT RIGHT X Y Z L R` (Saturn pad bits).
* A **scenario** is a Python function driving `Drv`; put yours in `tools/scn_<name>.py` (`SCENARIOS = {"name": fn}`, `START_AT = {"name": 0x06022894}` = enter that screen handler directly, `PATCHES = {"name": [(addr, bytes), ...]}` = the state the earlier screens would have left, written before the start in the oracle and by the C test after its boot).  `python tools/menu_oracle.py <name>` records `extracted/oracle/menu_<name>.mtr` (memory snapshot after boot, then the changes of every tick + the pad of every tick).
* `tools/test_menu.sh <name>` (in WSL: `wsl -d Ubuntu -- bash -c "cd /mnt/<drive>/path/to/sega-rally-psp-release; bash tools/test_menu.sh <name>"`) builds the port with gcc and replays the trace: **after every tick all compared regions must be identical** (HWRAM from 0x0603D880, LWRAM, VDP1 VRAM, VDP2 VRAM, colour RAM, VDP2 registers) except the ignore list.  It prints the first differing tick with address / expected / got and the V-blank recipe bytes of the tick.  `MENU_PROGRESS=1` prints progress.  `tools/test_menu_all.ps1` re-records and checks `tools/menu_scenarios.txt` (add your scenario names there).
* `python tools/menu_cov.py <scenarios> <lo> <hi>` : which instructions of the original your scenarios executed.  A scenario set is good when every branch you ported ran (confirm / cancel / every cursor position / time-outs / unlock combinations).  Press every button.
* The Windows shell mangles backslashes in here-documents (`\n` becomes a real newline in a C string, `\b` a backspace): **edit C and Python sources with the editor tool, or avoid backslashes in shell patches**.

## 4. Porting rules

1. Port function by function from `lift.py --c` + the raw disassembly, keep the original's order of effects, put `/* 0xADDRESS */` on the definition line, register every function whose address can be stored into a vector.  Name things after the original symbols when `functions.tsv` has one; otherwise `fn_XXXXXXXX` or a descriptive name.  Write the state variables you understand as comments (see the top of `src/menu_mode.c`).
2. Do not "improve" behaviour.  Quirks of the original (junk registers feeding stores, long stores in a 16-bit routine, counters that stop advancing when a z-bucket is full) are reproduced because the test compares memory.  If the original reads an uninitialised register, find out what it held (raw disassembly, trace in the harness) before deciding.
3. Anything that cannot be exact because it is hardware (CD, SMPC, BIOS, sound CPU) is a stub with a comment and a line in `tools/ported.txt` (`0xADDR - name  # why`).  The ignore list in `tools/test_menu.c` may only grow for such regions, with a reason; **never widen it to hide a difference in game state**.
4. New shared helpers go into your own `src/menu_<screen>.c` as `static` functions (with the original address comment); sibling ports may duplicate a helper, the duplicates are merged later.  Only append to the shared headers.
5. The test must pass from boot to the end of the scenario; commit nothing derived from the disc (`extracted/` is ignored).

## 5. What the original's screens share (already ported)

`src/satlib.c`: rcopy / rfill, the scroll / window / rotation-parameter smoothing (`set_*_int`), VDP init (`init_gspr`, `init_oscroll`, `tv_on/off`), `pad_read` (the host's pad words), swclear.  `src/menu_lib.c`: box copies / fills, colour offset and fades (`pre_fade_inout`, `fade_inout_work`), picture table loaders (`cd_map_set2`, `cd_color_set`), `key_repeat`, `delete_nbg0`.  `src/menu_sprite.c`: `draw_sprite` (VDP1 sprite command at 0x060C0000 + index * 8, z-bucket entry), `setup_texture`, `mkpoly_init`.  `src/sat_boot.c`: the power-on sequence and the main loop, the save-data defaults (`rec_init`).

## 7. Things learnt that bite

* Constants loaded before a branch are used after it; the lifter prints them (`r9 = 2;   // const`) before the branch.  Trust the printed C, then check the raw code.
* `FUN_xxxx` called with `r14` / `r13` / `r8` preset: look at the call comment.
* Word-sized stores of a register hold only the low 16 bits (`W16(addr, r0)`), loads sign-extend (`RS16`) - keep the signedness the original uses (`RS16` vs `R16`).
* The oracle never clears the z-bucket counters (game_zsort is stubbed), so after a few frames `draw_sprite` stops advancing the command index: that is the reference behaviour.
* Pad: the harness presents the Saturn pad word; `0x060AA990` = held, `+2` edge, `0x060AA994` = latched presses (cleared by the screen).  The PSP port maps PSP buttons to these bits (cheat codes use X / Y / Z).

## 8. Saturn button text

The pictures contain text like "CONFIRM WITH C BUTTON".  Find the cells / bitmap region with `d.shot`, then the converter (`tools/conv_menu.py`, to be written when the first such screen is ported) redraws the text with the PSP's button names (confirm = X) into the same cells with the picture's own letter style.  Record each occurrence in `docs/menus.md`.

## 9. Learnt while porting the record screens and the save code

* **Subroutines that end their caller**: `rec_dataset`'s helper `FUN_0602C9C0` finishes with `bra <caller's epilogue>` (the caller's saved `pr` is popped and the caller returns), so only the first `bsr` to it runs.  `lift.py` shows such a call as an ordinary call that "falls through"; read the raw code after every `bsr` whose callee ends in a `bra` to a foreign address.
* **Registers left behind are state**: the screens store `r5` after calling a merge routine (`[0x060A8C20] = r5`); the callee's last value of the register is part of the memory the test compares.  Port the callee's final register value (the merges return it: `record_merge3` returns the current key of list 1, `record_merge2` / `record_merge16` the end pointer of list B).
* **Implicit registers**: the hand written assembler of `rec_*` / `bup_file` uses `r11` .. `r14`, `gbr` as globals (`r14` = the page block 0x06040040 and later the action slot, `r13` = 0x060A8C14, `r12` = the key word, `gbr` = 0x06042A30 / the action slot).  Write the C with named constants for them and check **each callee** for stores into r11..r14 before assuming it preserves them (`record_menu_init` / `FUN_06032D84` clobber them; the main loop pushes and pops r11..r14 around the call).
* **Tables inside code**: jump tables become `switch`; every other table the C reads (cursor, sprite, picture request blocks, the vdp2 register words) must be in `ROM.blk`: add `(start, end)` to `EXTRA` in `tools/conv_menu.py`.  An index outside a table silently reads code bytes (the oracle does too): keep patched test values inside the real range.
* **Testing a function that no screen reaches in the oracle**: `START_AT` can be any original function that needs no register arguments (`rec_dataset`, `bup_main_save`, `adv_recordact_init` ..): the first pass runs it and the main loop continues with the main vector, so a scenario that patches the main vector word `0x060A001C` with the function's own address runs it once per pass (state machines like `adv_recordact`).  The state it needs is set with PATCHES (static bytes written before the start).  A scenario cannot change memory in the middle of the run (the test would not know): stage the state with PATCHES or with pad words.
* **Random tours are cheap and effective**: `mk_walk` in `tools/scn_records.py` presses random directions / shoulder buttons with random waits and a few held keys; `python tools/menu_cov.py` (or the pc-set dump in the scratchpad notes: `Drv` + `menu_oracle.PATCHES`) then lists what the tours never reached, and the missing combinations are added as START_AT scenarios with patched state bytes (`rec_ret_q*`).
* **Line endings**: files written with Python's text mode on Windows get CRLF; `tools/*.sh` must stay LF (WSL bash breaks on CR).  Write them with `newline=''` or use the editor tool.

## 10. Learnt while porting the photo module (staff roll, docs/menus.md 14)

* **The oracle's stubs can be wrong.**  `tools/menu_env.py` stubs every function from 0x06015F90 to 0x060178A4 as "the sound driver interface", but 0x06015F90 .. 0x06016338 are scroll routines (functions.tsv module `scroll`: `clr_hscr_rr`, `set_grpara_int`, `set_rpara`, ...).  When a port differs from the oracle in a VDP2 / scroll table although the code reads the same, check `cpu.hooks` for a stub at that address.  A scenario can take stubs out of its own oracle run (`unstub_scroll` in tools/scn_photo.py: the scenario function runs after the screen was started and may edit `d.m.cpu.hooks`).  Observer hooks (`tools/pc_regs.py`, `tools/photo_calls.py`) must not replace an existing hook: they would run the real code instead of the stub (`pc_regs.py` now refuses).
* **CD requests have flags**: entry word +0 = 0 raw file / 2 scatter-load file, word +2 = 3 plain copy, 4 = a BPE stream expanded into the destination (loader 0x0600F154); the harness and `sat_cd_request` handled only the plain copy (the staff roll's STAFF.CG came out as garbage in the VDP2 pictures while both sides agreed).  `tools/conv_menu.py` `BPE_RAW` lists the raw files that are stored expanded.
* **Parts the port leaves to the host are left out of the comparison per scenario**: the pseudo patch `(IGNORE, lo + hi)` (tools/menu_drive.py, read by tools/test_menu.c) removes a memory range from the compare; the reason goes next to the list in the scenario file (the global ignore list of test_menu.c stays for hardware only).
* **Original quirks seen**: a function that `jmp`s to another with its own `pr` still pushed (`crs_adv_dataset`) makes the caller's epilogue pop the wrong return address, so a tail call runs twice; the `gbr` a screen starts with is what the main loop left (0x060AA990, the pad block), and a stray `mov.b r0,@(245,gbr)` writes there; delay slots of `bsrf` tables; the jump table indexed by a byte offset (the state values are even).
* **Dev aids**: `MENU_DUMP=hexaddr:len[,..] tools/test_menu.sh <scenario>` prints the expected and got bytes of those ranges on the first failing tick; `python tools/mtr_mem.py <scenario> <tick> <hexaddr> <len>` shows the oracle's memory at a tick (to see what the oracle did, not only the first difference); `python tools/pc_regs.py <scenario> <passes> <addr,..>` the registers at code addresses; `python tools/photo_calls.py <scenario> <passes>` the functions called (first pass, count); `python tools/rom_gaps.py <lo> <hi>` the bytes of the program image that ROM.blk lacks; `python tools/reqdump.py <addr>` a CD request block.


## 11. Learnt while porting the ceremony and the ending (docs/menus.md 15)
* **Code that falls through into the next function**: `ending_camera_act` (init 0x0601F4AE runs on into the pass body 0x0601F4C8), the staff state 0x0601F27A (into 0x0601F29C), `set_grpara` 0x06015F6C (2 bytes: loads r13, then set_grpara2).  Read the raw code at every end that has no `rts`; the lifter shows the stored next-state address but not the fall-through.  Also `crs_dataset` leaves its pr on the stack (the tail call runs twice).
* **An engine behind a hook**: when a screen runs the race engine, port the screen's own code exactly and call the engine through a hook with the original routine's address (`engine(addr)`); stub the same addresses in the oracle scenario (list them in the scenario file).  The engine's memory stays as the scenario patched it; `POKE` (tools/menu_drive.py) changes it at a tick, mirrored by the test.  Say in the docs what is not verified.
* **The harness stubs 0x06015F90 .. 0x060178A4** as sound, including the scroll routines 0x06015FBC .. 0x0601625C: un-stub them in a scenario that needs the sky's rotation parameters (scn_ending.py `stubs()`, scn_photo.py `unstub_scroll`).
* Matrix code that decides memory (a visibility test that advances an animation, a confetti's motion) needs the exact fixed-point matrices: `mat_*` in menu_ending.c (rotate: the `sincos` table at 0x060A15A0, `xtrct` of the 64-bit sum of products); `translate` leaves the old z translation in r5 (a later routine may read it as an argument).
* `python tools/menu_cov.py` does not apply POKEs: what only a poke reaches shows as never run there.
* A private PSP build next to the others: `CFLAGS='-DSEGA_BASE=\"ms0:/PSP/GAME/<stick>/data\"'` before `psp-cmake ..` (src/main.c then reads its data from there), then `tools/run_ppsspp.ps1 -Dist <dist>\SegaRallyPSP -StickName <stick>`; without it every build reads the data of `SegaRallyPSP`.
