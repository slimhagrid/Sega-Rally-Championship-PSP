# Sega Rally Championship (Saturn, USA) - menus, records and the other non-race screens (survey for M7 / M8)

Tags: **[V]** read / checked, **[I]** inferred, **[U]** unread.  This closes the M2 gap "menus not read" at survey level: which code and data belong to which screen, how screens are chained, what a screen leaves behind for the race.  Nothing is ported.
Sizes are code bytes of the DBG modules (`extracted/analysis/modules.tsv`; the whole program is 204,657 bytes of code).

## 2. How screens are chained [V]

* Two vectors.  The **main vector** `[0x060A001C]` is the per-frame handler of the whole program (NOTES.md, "Boot, main loop and game states": `loop { call *(0x060A001C); sync(2) }`); the menu screens use a **second, screen-local vector** `[0x060A8800]` (set by `*_init`, called from the screen's main handler, e.g. `g_select_main` 0x0601FAC4 calls `*[0x060A8800]` once per pass and loops until the VDP2 shadow flag `[0x060AA803] & 2` says the frame was shown), so a screen is a small state machine (`0x0601FB44` waiting, `0x0601FB6E` input, `0x0601FEA4` cursor move ...).
  Leaving a screen = writing the next screen's handler into `[0x060A001C]` (e.g. `0x0601FB1A`: `[0x060A001C] = 0x06022894` = `slt_mode_init`, i.e. back to the mode select; `0x0601FB38`: `= 0x06020010` = `c_select_init`, forward to car select).
* **The screens' result is a handful of globals** the race start reads (docs/drive.md `DriveCfg`): `[0x060AA860]` game type (0 arcade, 2 practice; 4 / 6 / 8 / 10 = VS variants), `[0x060AA87E]` course, `[0x060AA80A]` car, `[0x060AA809]` transmission, `[0x060AA808]` difficulty, `[0x060AA811 ..]` set-up bytes, `[0x060AA82E]` mirror, `[0x060AA81B]` / `[0x060AA820]` (reset to 2 by `g_select_init`, meaning [U]), plus the selection word `[0x06040010]` (the current menu row) and the cursor / scroll variables in `0x060A88xx`.  `g_select_init` (0x0601F844) clears them; `g_select`'s exit maps `[0x06040010] == 1` to game type 2 (practice), the arcade row leaves it 0.
* **Pad**: `[0x060AA994]` (digital word of player 1; the menu code tests bits 0x8000 / 0x4000 / 0x0100 / 0x0E00 for the two cursor directions, the enter button and the other buttons [I]) and the analog axis byte `[0x060AA99C]` (127 = centre, threshold +-30 for menus); `key_repeat` (rec_main) gives auto-repeat.
* **Pictures** are VDP2 screens: the `.DAT` files are scatter-load files (docs/render_pipeline.md 9; `tools/datfile.py`) whose type-2 blocks (BPE) go to VDP2 VRAM (0x25E00000 .. 0x25E7FFFF, e.g. `MD_SLT0.DAT`: 43,586 bytes to 0x25E60000 = the 512 x 256 background, 6,605 bytes to 0x25E00040 = cell data) and whose plain blocks go to Low WRAM 0x244000 / 0x247200 (map / name-table data) or work RAM 0x060B8400.. (palettes).  `tools/vdp2.py` already renders such layers (it runs the game's own set-up code), so every picture can be rebuilt as a PNG at conversion time.
  `SCRL_*.DAT` (title, start, one per stage `DST FST LST MST`, select `SLT`) are **not** scatter files (no header of that form): scroll / picture streams for `scroll::*` / `scrlmove::*` [U].
* Sound for screens: `SDSELECT.DAT`, `SDNAME.DAT`, `SDCERE.DAT`, `SDENDING.DAT`, `SDORGSEL/SNG.DAT`, `DJ1..5.DAT` (docs/sound.md).

## 3. Records and save data [I]

`RECORD.DAT` / `RECORD2.DAT` / `REC_RET.DAT` = record screen pictures; the data lives in the R block of the race (`R+0x30` best lap with its "new" flag, `R+0x38 + 4 * course` the sum of all laps - the values the race clock ports compute, docs/drive.md 2a) and in the record buffers at 0x060AA400 (lap / split lists of the best runs; the `R+1` compare mode shows a stored run).  `rec_dataset` builds the per-course tables from those, `rec_asort` / `rec_tsort` rank them, `bup_*` writes them to the console's backup memory (`BACKUP.DAT` is the picture / font of the backup screen's messages, not a save template [V]; the save format is in 9.4).
For the PSP the equivalent is a small save file in `ms0:/PSP/SAVEDATA`; the format can be ours as long as the in-game tables are filled the same way (the ranking rules are in `rec_asort` / `rec_tsort` [U]).

## 4. Plan (M8)

1. Convert the pictures: for every menu `.DAT` render the VDP2 layers once with `tools/vdp2.py` (palette variants: cursor blink, bright / dim) and store as PSP textures (`conv_menus.py`).
2. Port the screen flow as a table-driven state machine (screens, cursor rows, transitions) and the globals above -> `DriveCfg`.  The pad logic is small (cursor, A = enter, B = back, key repeat).
3. Race results / name entry / records on top of the race clock (done in M6) and a PSP save file.
4. Ending / podium reuse the race renderer (camera + car + `ENDING.MAD`).

Size of the job: ~100 KB of SH-2 code, but a lot of it is picture bookkeeping that the converter replaces; the state machines themselves are small.  The only game logic worth reading line by line is `rec_*` ranking, `tm_attck` unlock flags, `option_main` and the result / handicap rules.

## 5. Unread

Every menu handler body (cursor tables, the exact transitions, unlock conditions, the option list), the attract demo scripting (`advFrmCtrl`, `set_advdata`), `scroll::*` picture streams (`SCRL_*.DAT`), the BUP library calls, `PHOTOTBL.DAT`, the replay system (`REPLAYD.DAT`, `RPYPDATA.DAT`: recorded inputs + voice files, `replay_sdctrl`).

## 6. Menu harness (M8 start, October 2026)

`tools/menu_env.py` boots the original program headless (`poweron_start` .. the main-loop copy at 0x060A0000) and runs any screen's handler: BIOS vectors are `rts` stubs, the BUP table returns 0, `cd_file_init` / the file loader 0x0600F354 / 0x0600F550 load the disc files, the slave handshakes are skipped (jobs run at once), the sound start-up and the sound command push are no-ops, the polygon pipeline (`draw_course`, `game_zsort`, the draw functions) is hooked out, SMPC status reads 0, `pad_read` (0x06005A18) is replaced by the harness' pad words (`Menu.pad`, Saturn bits: R 0x8000, L 0x4000, Down 0x2000, Up 0x1000, Start 0x0800, A 0x0400, C 0x0200, B 0x0100 ...; the game reads the held word at 0x060AA990 and the latched presses at 0x060AA994).
**A screen handler does not return each pass**: it loops `... intm_sync(n)` (0x0600521C, stores n in 0x060AA800 = the V-IN recipe, waits for the V-blank handlers) until the screen is left; the harness takes the V-IN / V-OUT handlers there (`_interrupt`) and hands control back (`Menu.run()` = one pass).  Handlers that do return (the title's `adv_main`) get the main loop's `sync(2)` instead.
`tools/vdp2_screen.py` renders NBG0-3 / RBG0 (tiles or bitmaps, 16 / 256 / 2048 / 32K colours, one- and two-word names, 8x8 / 16x16 characters, plane sizes, scroll, rotation, priorities, back screen; character n is the cell at VRAM n * 0x20 whatever the colour depth; the colour RAM is the shadow at 0x060B8000 until the V-IN recipe copies it) from the harness' memory; `tools/menu_shot.py <vector> [passes] [name]` and `tools/menu_flow.py "<passes>:<buttons> ..."` save pictures.
Seen so far: the title (state byte `[0x060AA807]`, state 14 = "Press Start Button", START is accepted in states entered after 0x060AA803 bit 6 is set), the mode select (`slt_mode_init` 0x06022894: the logo is RBG0, the labels NBG3), SELECT GAME (`g_select_init` 0x0601F978, 10 s countdown).  The car select, course select, time attack, options and record screens need the VDP1 sprite layer (not composed yet) and their own prerequisites.

## 7. Port method (October 2026)

The screens are ported exactly, on a memory model of the console, and checked tick by tick against the original: see `docs/menu_port_guide.md` (architecture, tools, rules, pitfalls).  Findings about the original that came out of the first ports:
* The program runs on a fixed main loop (copy at 0x060A0000: `[0x060AA801] = imm; call *[0x060A001C]; sync(imm2)`), and two interrupt handlers selected by recipe bytes (`[0x060AA800]` V-IN, `[0x060AA801]` V-OUT): VDP1 command table DMA, colour RAM / rotation-parameter DMA, scroll smoothing, frame swap handshake.  A recipe may rewrite both bytes, so one `intm_sync(n)` can take several V-blanks.
* The mode select (0x06022894) is a state machine on `[0x060A8800]` with 15 states, shows two VDP1 sprites per mode and a 3D car turntable, and contains two cheat codes: X+Y held sets bit 1 of the unlock byte 0x06040062; the pad sequence X Y Z Y X sets bit 2.
* Save data (backup memory) is the block 0x06040000.. (options 0x06040010 ..., unlock byte 0x06040062, record tables 0x06041000 / 0x06041110 / 0x06041220 / 0x06041E20, name tables 0x06042A38 ...); the factory defaults come from PRGDATA (`rec_data_init` 0x0029EA98, `rec_table_init`, `cmp_table_init`).

## 8. Time attack screens (src/menu_timeattack.c, scenarios tools/scn_timeattack.py)

Ported exactly from `cs_tm_attck` (0x06024068 ..), the picture setters of `cs_tm_att_pset` (0x0602552C ..), the sprite / car calls of `cs_poly_set` / `cs_car_set` and the line scroll helpers of `line_scrl` (0x060267A8 ..), and checked tick by tick against the original (21 scenarios `ta_*`, 500 - 11 000 ticks each, see tools/menu_scenarios.txt).  `tm_set_tm_att` 0x060262A4 (the entry the result / name entry screens use: sets the screen up from scratch, fades in, hands over to `tm_attck_main`) and `return_tm_att` 0x06026284 are ported too (scenarios `ta_entry`, `ta_entry2`, `ta_entry3`, `ta_return`); `set_pict_result` 0x06026162 (result screen pictures) is not: the result screens load its data.
Entered from the mode select (cursor 1: `slt_mode_main` sets the main vector to `tm_attck_main` 0x0602425C; while the mode select slides out it already calls `set_pict_tm_att` 0x0602552C = loads `TM_ATT0.DAT` and puts the first pictures).  Left to the mode select (`[0x060A88EA] = 1`, B on the first page) or to the race start (`[0x060A88EA] = 2`, `start_init` 0x06015408, not part of the menus).
* **Pages** (the state handler `[0x060A8800]`, page number `[0x060A88D6]`): 0 car (0x060243D6: rows celica / delta / [stratos] / [tuned car], cursor `[0x060A88A4]`, last row `[0x060A88FE]` = stratos + tune + 1), 1 tuned car list (0x06024574: records at 0x06040064 + 8n, n = `[0x0604002A]` = bit length of the tune byte 0x06040063), 2 transmission (0x060246DE: `[0x060A88AC]` 0 auto / 1 manual), 3 course (0x060247CE: courses 0..2, 3 = lake when bit 2 of 0x06040062 is set; `[0x060AA87E]`, Y + C held = mirror `[0x060AA82E]` bit 0), 4 lap mode (0x060248C6: 3 laps / free run, `[0x06040028]`; free run = game type 6).  Confirm = START / A / C (`[0x060A88DE] = 1`), cancel = B (-1).  The unlock bits: stratos = bit 2 of 0x06040062 (`check_stratos_flg`), lake = bit 1 (`check_lake_flg`), tuned cars = the byte 0x06040063 (`check_tune_flg`).
* Page changes slide the labels with the VDP2 line scroll table (0x25E7FE00 + 4 * line, `lscrl_plus` / `lscrl_minus`: lines 10 .. 25) and the VDP1 sprites ([0x060A882C] car picture position, [0x060A8830 / 34 / 38 / 58] the picture sprites, `spr_plus` / `spr_minus`): states 0x06024E18 / 0x06024F18 (car <-> tuned list), 0x06024F9A / 0x0602513C (-> course page and back), 0x06025268 / 0x0602537A (course <-> lap page), the second handler `[0x060A8808]` 0x06024D1A / 0x06024D3A / 0x0602542A / 0x0602544E (the car picture / course picture sprite slide while `[0x060A88E4]` is non-zero).  After each page the record box (best time of the course / car / lap mode: `record_connect` 0x0602C9E8 -> digits into the NBG1 cells at 0x25E38AC2 / 0x25E38B42 / 0x25E38BC2 / 0x25E38C42) and the picture highlight (`tm_pict_bright` 0x0602573A, `pict_bright_tmlay2` 0x06025AFC, tables at 0x060257CC / 0x060257E0 / 0x06025B54) are redrawn.
* **Quirks of the original that the port reproduces** (the test compares memory): `pad_check` 0x06024A60 takes a mode in r2 but `key_repeat` overwrites r2, so left / right (`[0x060A88C4]`) are read whenever DOWN is not held, with r4 leaking from the UP test; the slide states test `r11 == 1` ("a scroll line has arrived") and r11 is never cleared by them: it keeps what `tm_pict_bright` (a table pointer), `pict_bright_tmlay2`, `pre_fade_inout` (the fade step) or the car drawing (`dispSelectCar2` leaves a leftover constant, 0x2800 / 0x2000 / 0x1c00 seen) put there; `spr_plus` / `spr_minus` clamp the x half of the position word but add the sign-extended y half, so the clamped x is one less when y is negative.
* Found in shared code while porting: the mode select's `disp_car` omitted the second car's turn (the slave job 0x060265BA: `[0x060E5590] -= 128`, offset `[0x060A883C]`), the oracle did not hook `draw_offset_polygon` 0x060189B8 (the car / course polygons landed in the VDP1 command table between the sprites), `tools/test_menu.sh` built the PSP-only `menu_host.c`.
* **What the PSP host reads**: the turntable car block 0x060E5180 (+92 model type = car 0 celica / 1 delta / 2 stratos / tuned car model, +16 yaw (+128 per pass), +12 / +20 position, set by `set_car` of the mode select) positioned by the word `[0x060A882C]` (x << 16 | y, slides with the pages); the course model block 0x060E5100 (+0x24 model pointer = table 0x06023C04[course]: 0x06066C74 ..., +12 / +16 / +20 position, +24 pitch, +28 yaw (+128 per pass)) on the course / lap pages (`[0x060A88D6]` > 2); the light `rotate_light(0xA000, 0, 0)` (stub, `set_light_obj`).  VDP1 sprite commands (draw_sprite, z 0x10000): car picture `[0x060A8858]` with the descriptor table 0x06023D38[car] on pages 0 - 2; on pages 3 / 4 `[0x060A8830]` the car picture (table 0x06023DF8[car]) and the transmission mark (0x06023E14 / 0x06023E1C[transmission]) 0x200000 to its left, `[0x060A8834]` the course picture (0x06023E04[course]) and `[0x060A8838]` the fixed descriptor 0x06048310.
* **Pictures**: TM_ATT0.DAT = VDP2 cell data (blocks 0x25E10040 / 0x25E18000 / 0x25E20040) + the map tables (LWRAM 0x00244000).  The text pictures (CAR SELECT, car names, COURSE SELECT, course names, SELECT LAPS, 3 LAPS / FREE RUN, the best time box) are 16-bit cell maps in the NBG1 plane 0x25E38000 (destinations 0x25E384AE .. 0x25E38C42, cell = (dst - 0x25E38000) / 2: column, row = / 64); the title picture "Time Attack" and the frame are the 44 x 28 map at 0x25E3A000 (NBG2).  The rendered pages (car, tuned car, transmission, course, laps, with the stratos / lake / tune entries unlocked) show no Saturn button names.  The VDP1 sprite pictures could not be checked (the harness' VDP1 render has no sprite list at the pages); the sprite sources are the textures of the descriptors named above.

## 9. Record screens and save data (src/menu_records.c, menu_rec_data.c, menu_rec_disp.c, menu_bup.c, sat_save.c; scenarios tools/scn_records.py)

Ported exactly from `rec_main` .. `rec_menu2` (0x0602C6C0 .. 0x0602F490), the header drawing of `res_timeact` (0x06032D84), `rec_change`'s title demo helpers (0x0602E5F0 / 0x0602E638) and the data code of `bup_file` / `bup_freeze` / `bup_lib` (0x0602F5BC .., 0x06034C04 ..).  Entered from the mode select (cursor 4: `slt_mode_main` sets the main vector to `record_main` 0x0602CC74; while the mode select slides out it calls `record_pict_init` 0x0602D38E through the table at 0x06023078 = loads `RECORD.DAT`, and `set_pict_next_md` 0x06023918 (now ported in `menu_mode.c` for the entries 4 and 5) copies its picture data).  `record_main` is a blocking function like the mode select: it sets the main vector to `slt_mode_init` 0x06022894 at once (the exit target) and loops until the exit state sets `[0x060AA803]` bit 1.

### 9.1 The screen
* **State**: `[0x060A8C10]` screen state (0 running, 1 fade in, 2 fade out); `0x06040040` ("P") = the page state block, one byte per menu level, `0x060A8C14` ("Q") = `+0` header redraw request (`record_head_draw` = FUN_06032D84), `+1` page change request, `+2` page change state (`[0x060A8C12]` slide state: 0 out, 1 in, 2 done; `[0x060A8C30]` slide position).
  P: `+0` level 0 (4 / 5 = the ARCADE / TIME ATTACK choice, 2 = idle on a page, 11 / 12 = slide out / in), `+1` arcade page (4 = by course, 5 = by car), `+2` arcade course list, `+5` arcade course ranking, `+3` time attack course (arcade: the car list), `+4` time attack car, `+6` time attack set-up (`[0x060AA811]`), `+7` time attack transmission (`[0x060AA809]`); `+8` mode (4 arcade, 5 time attack), `+9` arcade page type, `+10 .. +15` the remembered cursor of each level (10 arcade course, 11 time attack course / arcade car, 12 car, 13 arcade ranking, 14 set-up, 15 transmission; 4 .. 7 = the rows, 4 on the lower levels means "all": the lists are merged by `record_sort_*`, 7 needs the unlock bits).  Bytes `+8 .. +15` survive between visits (initial 04 04 04 04 04 05 05 04, set at boot by `record_sel_init`).
* **Keys** (`key_repeat`, auto repeat 32 / 9 ticks; r12 of the original): up / down move the cursor of the current level (the page is redrawn through a slide), right enters the level below (the page slides out to the left in 8 steps of 14 line scroll units: `rec_menu_scrR`...), left goes back; the shoulder buttons R / Z and L / X (pad word bits 0x90 / 0x48, read raw from `[0x060AA990]`) move the scroll arrows (`cmarkact`); **B (0x100) leaves** (fade out, then `[0x060AA803]` bit 1); A / C / START (0x600 with a highlighted row of the time attack list = the player's own run) start the **replay** of that run (`record_replay_start`: the stored run's settings go to the race variables, `[0x060AA860] = 4`, main vector `0x06015408`, `[0x060A8C17] = 1` = "returned from a replay").
* **Return from a replay** (`[0x060A8C17] == 1` at entry): `FUN_0602CE30` rebuilds the video set-up, loads `RECORD2.DAT` (`record_pict_init2` 0x0602D388) and `set_pict_record` (0x06023A08), then the screen fades in.  `rec_dataset` also skips its set-up then.
* **Actions** (VDP1 sprites, objects of 0x80 bytes run through `FUN_0601BB02` / initialised by `FUN_0601BB5C`, ported as `act_run` / `act_init`): `coract` 0x0602F02C (the cursor frame, slot 0x060E4100), `markact` 0x0602F194 (the mark of the highlighted course / car row, 0x060E4180), `cmarkact` 0x0602F2B4 (the scroll arrows, 0x060E4200); sprite descriptors at 0x060480E0 .. 0x06048630 (from PRGDATA).  The blink counter `[0x060A8C38]` and the row of the player's own record `[0x060A8C39]` (-1 = none) drive the colours written to VDP2 VRAM 0x25E7FE4C / 0x25E7FE50.
* **Pictures**: `RECORD.DAT` (pages, VDP2 plane cells 0x25E3xxxx, tables from LWRAM 0x00244000 / 0x00223200), `RECORD2.DAT` (return picture set).  The pages show titles and rankings only; **no Saturn button text** appears in the record pages themselves (the ranking digits, names, the car-class and flag glyphs are cells of the 0x25E3xxxx planes).  The text of the backup screen (see 9.4) names buttons, but that screen is not shown on the PSP.

### 9.2 Record data
* 384 records of 8 bytes at **0x06041220 .. 0x06041E20**: `u32 time` (BCD `0x00MMSSCC`; ascending = better; 0 = unused), `u32 info`: bits 28..29 car class (0 / 1 / 2 / 3 -> glyph 0x312C + 12 * ...), bit 30 + bit 24 = the two flag glyphs (`0x2086 + 4 * bit24 + 8 * bit30`: transmission / AT-MT), three name letters in bits 16..20 / 8..12 / 0..4 (0 = blank, 1 .. = letters, glyph `(n + 39) * 2`).  The save packs a record into 5 bytes (`rec_data_expand`: 21-bit time, class / flags 3 bits + 16 bits of name).
* `rec_table` **0x06041000** (68 pointers, filled from PRGDATA 0x0029F698 at boot): +0x00 4 arcade course lists (16 records each), +0x10 4 arcade car lists (8 records), +0x20 the time attack lists: 4 courses x (4 cars x 2 x 2) pointers = 64 entries (6 records each, 5 are shown + the best-lap row); `cmp_table` **0x06041110** (parallel, from 0x0029F7A8) points into 0x06041E20 .. 0x06042A30 (lap time lists).  `0x06042A38 ..` the name / mark block (the `rec_dataset` inputs: +0 / +1 / +2 car, level, ..., +3F option nibbles), `0x06040062` the unlock byte (bit 1 / 2 = the cheats of the mode select, bit 4 = the arcade course ranking is unlocked).
* **rec_dataset** (0x0602C6C0, `[0x060AA860]` game type 0 / 2 / 4 / 6): builds the race's comparison data: `0x060B0500 ..` (the best times of the course for the HUD), the lap sums into `0x060AA538` (16 / 48, 15 / 12, 18, 6 laps; a BCD carry once past 10:00 - the original's `FUN_0602C9C0` also ends `rec_dataset` itself, so only one sum runs), the stored replay of the course (0x002C0000 + course * 0x3D00).  **rec_connect** (0x0602C9E8): the list pointer (r0) and comparison pointer (r1) of the current mode / course / car (mode 4 with r4 = 1 merges the 12 lists of the course with `record_sort_c`).
* **Ranking rules** (`record_merge3` 0x0602E968 / `record_merge2` 0x0602EA0E / `record_merge16` 0x0602E8AC, wrappers `record_sort_a/b/c`): lists are merged by time (signed compare, the earlier list wins ties); `merge3` merges the 3 lists whose pointers are 16 bytes apart and only looks at the third list when unlock bit 2 is set; each output row has a "source" tag at +48 (the list the row came from).  `record_insert` (0x0602E8EA) inserts a new time into such a list (used by the name entry / result screens): the car / transmission bytes go into the info word, the name is 'AAA' (0x1B1B1B), the address of the new row is stored at `[0x060A8C70 + r8]`.
* **Rows** (`disp_row` 0x0602EC90 / `rank_loop`): rank number (equal times share the rank), time, name, flags, car class glyphs; the row that equals the player's run (time, car class, flags vs the stored replay) is drawn in the highlight palette (+0x4000 cells) and its row number is kept in `[0x060A8C39]`.  Quirks reproduced: the request code stores the register r5 that the merge routines leave behind (`[0x060A8C20]`), `FUN_0602C9C0` / `0x0602F3xx` end their callers, `adv_scroll` reuses the negated offset of the previous line.

### 9.4 Save data
* **Two backup files** (the original writes them through the BIOS backup library, vector table at 0x06000354, `BUP_Init` at 0x06000358): `SEGARALLY_0` (comment "RECORDS", 0x13C0 bytes) = the image at **0x060EEC00**: 384 x 5 bytes of records (0x060EEC00 .. 0x060EF380), the 0x302 longs at 0x06041E20 (0x060EF380 ..), the 0x22 bytes `0x06040062 ..` masked unlock byte + options (0x060EFF88), 14 bytes of `0x06042A38 ..` (0x060EFFAA), and at **0x060EFFBC** the checksum `9 + sum of the 0x4EF longs of the image`; and `SEGARALLY_1` (comment "GHOSTS", 0xF400 bytes) = the four stored replays at **0x002C0000** (0x3D00 bytes each: +0 checksum `9 + sum of the following longs`, +4 the 4 times, +20 car / transmission / .., +24 5 setting bytes, +32 the best-lap list, +104 the recording 0x3D98 bytes from 0x002CF800), only ever on device 1 (the memory cartridge: 62 KB do not fit the internal 32 KB).
* **Control bytes** (the original's gbr block `0x06042A30`, zeroed by `rec_init`): `+0` screen state, `+1` message, **`+2` device of SEGARALLY_0 (0 internal / 1 cartridge)**, **`+3` save mode (0 = nothing is saved, 1 = records, 2 = records + replays)**, `+4 / +5` flags (+5 = 1: the backup screen has run once), `+6` factory records in use.  The saving routines do nothing while `+3` is 0; the backup screen (0x0602F64E, between the title and the mode select) is what sets them after checking the memory.  **The backup screen and its library operations (0x06034614: format / stat / delete / copy with message boxes) are not ported**: on the PSP there is nothing to check.  `bup_host_attach(cartridge)` (menu_bup.c) leaves behind what the screen leaves when the internal memory works (`+3 = 1`, or 2 with a cartridge); the PSP host registers it as the original's screen address 0x0602F64E (`bup_screen_skip`: attach, then the main vector goes to the mode select).
* **Host side** (src/sat_save.c): `sat_save_open(dir)` (call before `sat_boot()`; the boot's `rec_init` -> `bup_load` reads the file), `sat_save_open(NULL)` = no backup memory (the factory records, nothing is saved), default = stub (the oracle's BIOS: every call returns OK and does nothing; the tests run in this mode), `sat_save_cart(1)` enables device 1 (1 MB).  Each device is one image file `<dir>/BUP0.BIN` / `BUP1.BIN` ("SBUP", version 1, formatted flag, file count, then the 34-byte BUP directory entry + data per file; written atomically after every change).  The library model keeps the return codes of the real one (OK 0, NON 1, UNFORMAT 2, NOT_ENOUGH_MEMORY 4, NOT_FOUND 5, FOUND 6, NO_MATCH 7), 64-byte blocks (one directory block + data), dates as minutes since 1980-01-01.  The vector offsets the game uses: +8 BUP_Format(dev), +12 BUP_Stat(dev, size, &stat), +16 BUP_Write(dev, &dir, data, mode), +20 BUP_Read(dev, name, data), +24 BUP_Delete(dev, name), +40 BUP_SetDate(&date).
* Load = `bup_load` (0x06034C04): `BUP_Init`, then 3 tries on device 1, 3 tries on device 0, each = `BUP_Read` + checksum (`bup_check_main`); any failure = the factory data (`rec_defaults`).  The real BIOS reads into the buffers 0x06042A00 / 0x06046A00 as its own work area; the model does not.
* Tests: `tools/test_save.sh` (unit test: save -> power cycle -> load, a damaged image, no memory, the library on a 1 MB cartridge, dates); the oracle tests call `bup_main_save` / `bup_replay_save` directly (scenarios `rec_bup_*`: the stub BIOS does nothing, the packing and the replay bookkeeping are compared).

### 9.5 Scenarios (tools/scn_records.py, extended list tools/menu_scenarios_rec.txt)
`rec_enter`, `rec_exitA/B` (leave with A / B), `rec_full0..6` (every level entered, left and cycled up / down with each unlock combination), `rec_tour0..3` and `rec_walk0..5` (random walks through every page with the unlock bytes 0 / 2 / 4 / 0x10 / 0x16 / 0x14, patched record lists with ties, every class / flag / name, held keys, shoulder buttons), `rec_ds*` (`record_dataset` called directly for the game types 0 / 2 / 4 / 6 with and without a stored replay), `rec_ret_*` (`record_main` entered with `[0x060A8C17] = 1`: return from a replay, every merge combination of the time attack levels `rec_ret_q0..8`, the replay start `rec_ret_replay`, the exit by C), `rec_bup_*` (the save routines), `rec_adv*` (title demo header slide).

Function level: `python tools/fn_records.py` runs the original's digit writers, `time_disp`, `record_name_disp`, `record_insert`, the table writers (`rec_pal_set` / `rec_color_set` / `rec_vdp2_set_w`), the tile fills and the two checksum routines on the SH-2 interpreter with random registers / memory (795 cases, `extracted/oracle/fn_records.txt`), `tools/test_rec_fn.sh` replays them on the port (registers returned and the memory delta must match). ## 10. Arcade selection chain: SELECT GAME, car select, course select (src/menu_arcade.c, scenarios tools/scn_arcade.py)

## 12. PSP button names in the pictures (src/menu_pspfix.c, October 2026)
The Saturn pad is named in baked-in pictures.  The picture data stays as the game made it (the oracle tests compare it); on the PSP only, `pspfix_apply()` (called by `menu_host.c` whenever VDP2 VRAM was touched) redraws the texts in place.  A fix names a box of cells of a scroll layer (map address of the top-left cell, size in cells) and the FNV-1a hash of the box's original bitmap (all 8-bit cells, row-major); the box is only touched when the hash matches, so nothing else can be hit.  The new glyph is drawn procedurally in the colour indexes of the picture's own font (outline + shade ramp) and written back to the character patterns the box uses.
* **Fixes**: (1) arcade banner, NBG3, box 40 x 4 cells at 0x25E3CC04 (hash A85D1437; SELECT GAME, car select, course select): "CONFIRM WITH C BUTTON" -> X; (2) options page, NBG0, two boxes of 16 x 2 cells at 0x25E31434 / 0x25E31734 (hash 3DF4E385, SOUND / KEY CONFIG rows, the same character patterns): "press A or C button" -> "press X button" (the word "button" moves left); (3) records, NBG0, 16 x 2 cells at 0x25E33364 (hash ADEDF95A): "Press C button for Replay" -> X.  The PSP maps Cross to the Saturn C (confirm), Circle to B, Square to A.
* **Only the English / digital pad variants** are fixed: the wheel / analog banner variants and the Japanese ones (SCRL_SLT.DAT, see section 10) are not shown on the PSP (the pad kind is a digital pad, the language byte 1).
* **Finding more**: `PSPFIX_LEARN=1 build/render_mtr <trace> <tick> out.ppm` prints the hash of every fix box; `PSPFIX_SCAN=8 build/render_mtr <trace> 1 out.ppm` takes the first matching box as a template and searches all planes of the layer in every 8th tick for the same bitmap at other places (none were found in the oracle scenarios of the arcade, options, records, time attack, set-up and mode screens).  `tools/pspfix_layers.py` (which layer draws a screen rectangle, box bitmap, shared characters) and `tools/pspfix_probe.py` (decode a cell box) are the design aids; `render_mtr` writes `<out>.vram / .cram / .reg` for them.  Checked: `PSPFIX=1 build/render_mtr trace tick out.ppm` renders with the fixes.
* **KEY CONFIG page** (option page 3): `kc_update()` in menu_pspfix.c redraws both players' pictures as one picture on NBG0 (23 x 10 cells each, characters in the free VRAM 0x44000 .. 0x5FFFF): the PSP (art/psp_pad.png -> `tools/conv_pspad.py` -> data/menu/psp_pad.bin, 128 x 80, mapped to the grey scale of the Saturn picture), the text and underlines of the original labels (NBG1, hidden) and new leader lines to the PSP's buttons.  The eight label slots belong to Saturn buttons L, D-pad up, D-pad down, X Y Z, R, C, B, A; on the PSP in the race: L / R, D-pad, Triangle (X), Select (Y), Circle (C), Cross (B), Square (A).  The race (play.c, from the menus) reads the pad through the original's `config_keyset` rows (types A .. D = rows 0 .. 3 of 0x060086C8, row from `[0x060AA80F]`, set by rec_dataset): A = accel Cross, brake Square / Circle, shift up R, down L, view Triangle / Select.

### PSP host notes (menu_host.c)

## 15. The ceremony and the ending after the goal of the last arcade stage (src/menu_ending.c, scenarios tools/scn_ending.py)

### 15.1 The ceremony (0x0601E4E8 .. 0x0601EF34)
* `ceremony_init`: `init_gscroll` (0x06015B80, new: the scroll / window set-up and the sky's rotation parameters, DMA'd to VDP2 VRAM), CEDESERT.DAT (the ground and sky bitmap of the scene; always the desert file: the table 0x06004824 names it four times), the models (`set_car_texture` OBJECT.MAD, `set_ceremony_model` ENDING.MAD), three actors in the list of 64-byte slots at 0x060E4000 (+0 function, +4 next, +8 previous; head / tail [0x060D0078] / [0x060D007C]; `FUN_0601BC20` takes the first free slot, `FUN_0601BBE8` runs the list with the slot in gbr / r14), the car block placed by `FUN_0601EA76` (position (0.42, 2.13, -100.7), yaw -3.14 rad; the race's own end position is not used), 70 confetti pieces (0x060E4800 + 64 * n; the random generator 0x0601D6CC: r = r * 5 + 0x3537 at 0x060D0050), fade from white.
* `ceremony_main` is a blocking pass loop (like the other screens): sound call, `fade_inout_work`, the pipeline's frame init, `set_grpara` (the sky target from the camera's yaw: **0x06015F6C only loads r13, the code runs on into set_grpara2 0x06015F6E**), the actor list, the confetti, the state handler [0x060D0020], `intm_sync(38)`.  States: 0x0601E6DA (frame >= 92: fade to white, jingle), 0x0601E708 (frame >= 103), 0x0601E726 (sets the exit bit: its counter test `cmp/hi` on 0 - 1 is always true).  The frame [0x060D0118] (16.16) is published by the third actor and advances 0x8000 per pass **only while the animated model is on screen** (so the visibility test `FUN_0601D8D4` decides the length of the screen: the port runs it exactly with the 3 x 4 fixed-point matrices of the matrix module, `mat_*` in menu_ending.c).
* Actors: the **camera** (0x0601E7B4 / 7CE) walks a uniform cubic B-spline through four control points (`bspline` 0x0601BA04, parameter = frame * 2 / 210 from the on-chip divider), looks at the car (`get_lookat_angle` 0x0601BA6C with `atan` / `sqrt` of the math module) and builds the view matrix; the **car** (0x0601E9B6 / 9D2) calls `dispCar` (0x060101E8: only [car + 896] = the draw routine of its entry and [car + 900] = r5 are memory; the tyre marks of `FUN_0601D0E6` need [0x060D0148] != 0, which only the race's `dispcar_init(1)` sets: the port stops (`menu_unported`) if it is set, the PSP never sets it); the **animated model** (0x0601ED1C / 24) is the car again in 40 textured parts (ENDING.MDL, tables 0x0601EDE4 / EE8C: 104 frames of 20 bytes per part, `FUN_0601CF44` interpolates them).  The confetti (`FUN_0601EBB0`): fall by the rotated vector (0, 0x7AE, 0), spin, respawn above the car; its visibility test takes the **old z translation of the matrix as the radius** (translate leaves it in r5).

## 18. Renderer: line scroll and the NBG1 zoom registers (found from PSP photos, October 2026)

The oracle tests compare memory, not pictures, so three renderer gaps only showed on the PSP:
* **Line scroll** (`src/vdpr.c`, `setup_layers`): NBG0 / NBG1 with SCRCTL (0x25F8009A) line scroll X / Y / zoom now read their table (LSTA0 0xA0, LSTA1 0xA4; entries of 4 bytes per interval of 1 / 2 / 4 / 8 lines: scroll X, scroll Y, zoom X, the enabled ones).  The screens use it for the staggered slides: the options pages' rows, KEY CONFIG's page change, the **car set-up page's gauge** (1 .. 5 with SLOW / QUICK, SOFT / HARD ...: its NBG1 picture sits at the right edge of the plane and the line scroll table moves it to x = 136; without line scroll only its first letter showed at the edge: the PSP's "values cannot be seen").  Unzoomed layers with line scroll X keep the cached torus (every screen line has its own origin, `LCache.rox`); line scroll Y, line zoom and the vertical cell scroll (SCRCTL bit 0, not implemented: `vdpr_unsupported` bit 0) use the slow full rebuild.  `render_mtr` prints `vdpr_unsupported` after `-all`: none of the 141 scenarios use line scroll Y, line zoom or vertical cell scroll.
* **NBG1's zoom registers** were read from 0x80 .. 0x8E - 8 instead of 0x88 .. 0x8E (`0x78 + 16 * n`): a scroll position with low bits set in SCXIN1 made the layer zoom out 6 times.  The ranking screen's NBG1 (the RANKING header, RANK / NAME / TIME / CAR) showed as tiny yellow bits repeated four times across the top of the picture.
* **Slide out of KEY CONFIG** (menu_pspfix.c): the DIY / blank label cells are only written where the screen has drawn its TYPE cells (the original clears them when the page leaves: DIY stayed behind and scrolled down with the page); our pad pictures stay while NBG0 still shows them (state 8) and go when they have left the picture; `kc_off` leaves cells the next page has drawn into since (the options page's DIFFICULTY / CHAMPIONSHIP / TIME COMPARE rows had their right halves erased for a moment).
* The pictures of the screens that used these registers changed (menu perf hash comparisons against older renderers are not meaningful); `render_mtr <trace> -all` checks that the cached and the uncached render agree for every picture of a scenario.
* **Arcade chain: the rank byte** `[0x060AA300]` (`Drive.g300`) is a work RAM byte that survives from a stage to the next: the goal / game over code stores the player's rank byte there and `normal_plinit` copies it to the slot's +0xB6, which the opponents' spawn (initOtherGP) and the HUD's POSITION n / 15 read.  The host did not carry it (every stage started with a fresh `Drive`: "0 / 15" on stage 2); `PlayCfg.init_g300` / `PlayOut.g300` carry it through the console memory now (menu_host.c `host_race`).
