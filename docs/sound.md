# Sega Rally Championship (Saturn, USA) - the sound system (survey for M9)

Tags: **[V]** read in the disassembly / extracted data and checked, **[I]** inferred, **[U]** unread.  This is the M2 gap "sound driver not read": a map of the whole path from the game to the speakers, enough to plan M9.  Nothing here is ported yet.
Addresses: SH-2 side = `0RALLY.DAT` (base 0x06004000); 68000 side = sound RAM (SH-2 address 0x25A00000 + offset = 68000 address offset).  Tools used: `tools/sh2dis.py`, capstone's M68K disassembler on the expanded `SDDRVS.DAT`.

## 1. Architecture [V]

```
SH-2 game code ──push id──► byte queue 0x060AAA24 ──per frame──► command slots in sound RAM (0x25A00700, 8 x 16 bytes)
                                                                   engine words 0x25A007C0 (player 1) / 0x25A007E0 (player 2)
                                                           68000 driver (SDDRVS.DAT, stock Saturn sound driver) ──► SCSP (32 voices, DSP, 512 KB sound RAM)
CD-DA music (16 tracks) ──► CD block mixer (not touched by the 68000)
```

* **The driver is the stock Sega Saturn sound driver** (the "SEGA" tag at 0x5D6C that the reset code checks, the workspace at 0x7000, the command ring at 0x800 - 0xFFF, SCSP registers at 0x100000).  Three builds are on the disc: `SDDRVS.DAT` (1P, 15,740 bytes BPE-packed -> 23,920 expanded, loaded to 0x25A00000, plus a 530-byte block at 0x25A0A000), `P2SDDRVS.DAT` (2P / VS, 17,920) and `ESDDRVS.DAT` (ending, 17,630).
* Reset vector: SSP 0xA000, PC 0x1000.  The main loop at 0x1092 polls the host command slots (0x130E -> 0x1326), runs the sequencers and updates the SCSP voices every tick; commands are dispatched at 0x17F2.
* **Command slot** (16 bytes at 0x700 + 16 * n; the SH-2 fills slot n and the 68000 clears the first byte when it has taken it): byte 0 = command, bytes 2 .. 5 = parameters.  The driver moves each slot into its own ring at 0x800 and calls the handler for `command` (1 .. 0x1F, table at 0x1872; for 0x80 .. 0x90 a second table at 0x180E).
  Handlers seen: 1 = 0x18F2 (play: three parameter bytes + two more), 2 = 0x1910, 3 = 0x1958, 4 = 0x1962, 5 = 0x196C, 6 = 0x197A, 7 = 0x1982, 8 = 0x168E, 9 = 0x1990, 10 = 0x19B6, 11 = 0x19BE, 12 = 0x19C6, 13 = 0x19D8, 14 = 0x1A1C, 16 = 0x1E68, 17 = 0x1E56, **18 (0x12) = 0x1E4C**, 19 = 0x1E62.  What each does is [U] (the stock driver's documentation is not available; they are play sequence / stop / volume / pitch / ... in the usual order).
* **SH-2 sender** (`0x06016FD0`, once per frame): for each queued id (`0x06016FBC` pushes an id into the byte queue 0x060AAA24, at most 15 per frame) it writes `cmd = 1` and the four bytes of `table[id]` (`0x060A1330`, one long per id; `phys.dat` has it) into the next free slot; a second word queue (0x060AAA34, 4 entries) writes `cmd = 0x12` + one word (volume / pan updates).  Slot 8 (0x25A00780) ends the area, a full area drops the rest.
* **Engine sound** (`gamesd::game_se_set` 0x0601633C, `game_se_set2p` 0x060163EC): every frame the long at 0x25A007C0 (0x25A007E0 for player 2) = `69 + (engine word +0x8C >> 16)` (the pitch index follows the revs) and the long at +4 = volume `((+0xA0 * 16) >> 16) * 2`, capped at 15.  So the engine note is a looped sample whose pitch is driven directly by rpm: the PSP needs one pitch-shifted loop per car.
* **Sound ids** (the SH-2 code names them by number only; `table[id]` = `0x060A1330 + 4 * id`, bytes b0 b1 b2 b3, e.g. id 2 = `07 00 01 00`, id 3 = `07 00 02 00`, id 25 = `06 02 02 00`): b0 looks like a priority / level, b2 counts up through the sequence numbers 1, 2, 3 ... of the loaded bank, b1 selects the bank (0 = common, 1 / 2 = stage banks) [I].

### Who plays what (static scan of the calls to 0x06016FBC; id in r4) [V for the id, I for the meaning]

| id | caller | when |
|---|---|---|
| 1 | `laptime::check_lap` (9 sites), `time_adjust` | checkpoint / lap / extension chime |
| 2 | `gamesd::game_se_set` (0x06016398), `FUN_0601646C`, `FUN_0601BF80` | sent when the wheel contact sums cross a threshold (0x66555), i.e. an impact class sound [I] |
| 3, 4 | `FUN_0601646C` (road contact: gear shift, tyre, wall) | per-pass wheel events: bit tests of car +0xC6 (collision flag, set by the collision routines) |
| 7, 23, 24, 25, 26, 30 | `FUN_060165A4`, `FUN_060168A4`, `road_noise_fpsd`, `init_game_se` | tyre noise by surface (gravel / tarmac / water), skid, speed-dependent road noise |
| 22 | `FUN_06008BCC` (sound state of the car, the +0x364 .. 0x36F bytes the M6 test masks) | |
| 29 | `FUN_0601DC14` (heli) | helicopter flyover |
| 32 | `FUN_06016998` | |
| 75, 85, 86, 87 | `advctrl::a_title_wait`, `display3::count_down_start_replay`, `resreplay_display` | title, replay screen |
| -64 | `count_down_start_replay`, `FUN_060165A4` | (r4 = -64 selects a different queue / stop-all) |

The co-driver's voice is **not** an id of this table: the message byte `[0x060AAA45]` (29 .. 37 in the race; the port keeps it in `Drive.msg45`) selects a spoken phrase that the 68000 plays from the per-phrase voice banks `OOH.DAT`, `GET.DAT`, `TAKE.DAT`, `WAY.DAT`, `WHO.DAT`, `SMOKIN.DAT`, `SMOOTH.DAT`, `FENDER.DAT` (each 120 - 184 KB, loaded to 0x25A0B000 / 0x25A0C000 on demand, one phrase at a time) [I: the consumer of `[0x060AAA45]` is the display code `0x06013130 ..`, which also uses it to pick the message picture; the voice request path was not followed].

## 2. Sound RAM contents (what the files hold) [V layout, I formats]

| file | blocks (dest, bytes) | content |
|---|---|---|
| `SDDRVS.DAT` / `P2SDDRVS.DAT` / `ESDDRVS.DAT` | 0x25A00000 (BPE type 2), 0x25A0A000 (530) | the 68000 driver; the small block is the driver's work / map area |
| `SDDESERT.DAT`, `SDDESE_N.DAT`, `SDFOREST.DAT`, `SDFORE_N.DAT` (there are no Mount / Lake files: which bank those stages use is [U]) | 0x25A22100 (283,804), 0x25A6D38C (40), 0x25A6D3B4 (38 KB) | the stage's sound data: a container named `Q_demo3.EXB` ("EXB" = sequence + tone bank format of the Sega sound tools), then the stage SE bank; the `_N` variants are identical except for 429 bytes of the first (283,804-byte) block (purpose [U]) |
| `CELICA1..5.DAT`, `CELICAE.DAT`, `LANCIA1..5.DAT`, `LANCIAE.DAT`, `STRATOS1.DAT` | 0x25A0B000 (41 - 61 KB), 0x25A6759C (24,048, type 1), 0x25A7F000 (2,048) | per car: engine / tyre samples and tone table (the first block starts with an offset table 0x000A, 0x001C, 0x0026 ... followed by SCSP-ready PCM), a shared SE block, and a "PCM#00-" voice map (`50 43 4D 23 30 30 2D` = "PCM#00-") |
| `OOH, GET, TAKE, WAY, WHO, SMOKIN, SMOOTH, FENDER.DAT` | 0x25A0B000 (0.3 - 2 KB: sequence / tone map), 0x25A0C000 (115 - 180 KB PCM) | co-driver phrases |
| `SDCERE.DAT` (430 KB), `SDENDING.DAT` (409 KB), `SDSELECT.DAT` (290 KB), `SDNAME.DAT` (118 KB), `SDORGSEL.DAT`, `SDORGSNG.DAT` (0x25A1C040 / 0x25A14040) | 0x25A0B000 | the ceremony, ending, select-screen and name-entry jingles / music as sequenced data (the "ORG" files are the organ music of the title / extra screens) |
| `PCMDATA.DAT` (125 KB), `DJ1..5.DAT` (53 KB each) | 0x002DF000 (Low WRAM, **not** sound RAM) | PCM played by the CD block / SCSP direct path (the DJ voice announcements of the select screens) [I] |
| `GMGOVER.DAT` | 0x25E10440 (VDP2 VRAM, type 2), 0x00200000 | "GAME OVER" picture (not sound) |
| CD-DA | 16 tracks (`extracted/audio/trackNN.wav`) | the music: `_gfc_cdplay` (0x06017776) exists, so the music is presumably CD audio and the sequenced banks above are jingles and effects [I] |

The loader for all of them is the GFS `_gfc_load` path (`sound` module: `_gfc_load` 0x06016F20, `_gfc_ldbpe` 0x06017174, `_gfc_madload`, `_gfc_cdplay` / `cdpause` / `cdseek`, `_SoundOn` / `_SoundOff` 0x06016E54 / 0x06016E7A), driven by the menus and the race start (the loader table names `SDDRVS.DAT` / `P2SDDRVS.DAT`; which stage / car file is loaded when was not traced [U]).

## 3. What the PSP needs (plan)

1. **Do not run the 68000.**  Everything is deterministic data: pick one of (a) *HLE of the effects*: decode each bank's PCM + tone table once at conversion time (new converter `conv_sound.py`: EXB / offset tables -> 16-bit PCM + loop points), play with the PSP's `sceAudio` through a small software mixer driven by the same ids (the id -> bank / sequence table is in `phys.dat`); (b) *capture replay* like Snatcher: render every id once with a 68000 + SCSP model (the repository already has a 68000 interpreter in `../../SEGA-CD-to-PSP/Snatcher/tools/m68k.py`, no SCSP model yet) and ship the rendered samples.  (a) is preferred for the engine (pitch follows rpm) and the tyre noise (volume / pitch from speed); (b) is the cheaper way to get the jingles and sequenced music.
2. **CD-DA** (16 tracks, 431 MB WAV): re-encode to ATRAC3 / MP3 at conversion time; the track numbers per screen / stage come from the code (`_gfc_cdplay` callers) [U].
3. **Order of work for M9**: (i) event ids -> effects (checkpoint, impact, tyre by surface), engine loop with pitch, co-driver phrases; (ii) CD tracks; (iii) sequenced jingles; (iv) 2P banks.  The port already produces the events: `Drive` can emit "sound events" at the same call sites (`check_lap`, `FUN_0601646C` wheel contact bits, the HUD's red-digit beep, `msg45`).

## 5. What is ported (M9, state of 21 Oct 2026)

* **Sound system on the PSP** (`src/snd.c`, `m68k.c`, `scsp.c`, `snd_lib.c`, `snd_psp.c`): the original's 68000 driver runs on an interpreter (predecoded instruction cache, `M68K_NO_WH` build), the SCSP model mixes 44.1 kHz stereo (gain tables, integer accumulators; output is bit-identical to the first version, `extracted/snd/golden_*.raw`), the SH-2 sound library is ported function by function onto the memory model.  The SCSP's MSLC / CA monitor (0x100408) is modelled: the driver watches the position of the voice stream's slot with it.
* **Race events** (`src/sndev.c`): `game_se_set` (engine pitch / volume words, tyre / skid / road noise, wall and surface impacts, wall counters), the throttle-lift noises of `PowerGet` (`FUN_06008BCC`), the checkpoint / lap chime (id 1), the countdown's start sound and the music start, the goal / game-over screen's commands.  Checked **bit-exact against the oracle**: `tools/oracle.py run --snd` logs every call of the sound library plus the sound state per pass (`.snd`), `tools/test_drive.c -snd` compares (`bash tools/oracle_snd.sh`, `tools/test_snd_ev.sh`: 16 traces, 0 differences; the car's +0xC6 and +0x364.. bytes are compared in all drive traces now).  The 68000's status byte (the only input from the sound chip) is a deterministic stand-in in both.
* **Co-driver voice** (`snd_lib.c` `voice_start` / `snd_lib_vint`, FUN_0601708C / FUN_060170C4): a phrase number written to [0x060AAA45] (`SET_MSG`) is streamed from the work RAM into the sound RAM ring (0x25A7D000 / E000 / F000) by a state machine that runs once per V-blank (menus: every tick; race: before the logic and before the flush); not checked against the oracle (it needs the 68000).
* **Added later** (section 6): the CD music, the helicopter and start-line sounds, the replay timeline (`sndev.c` `replay_sdctrl`, `sndev_replay_start` / `_go`), the ending's music fade-out.  **Still not ported**: the 2P sound sets, the Time Attack new-best-lap jingle and the beep of the last five seconds of the clock.
* Development: `data/snddump` (empty file) writes `snd_dump.raw` (the mixed audio), `snd_stats.txt`, `snd_lib.txt`; `data/nosnd` runs without the audio thread.

## 6. Audio cost and the music (21 Oct 2026)

The menus were slow with the music on: the original's sequencer (68000 + ~20 SCSP voices) took about a fifth of the CPU (PPSSPP virtual time: 447 us of every 2018 us driver tick) next to the software VDP2 renderer.  What was done, cheapest first:

* **The songs of the menus are pre-rendered streams** (`src/bgm.c`, `tools/conv_bgm.sh`).  `tools/bgm_render.c` runs the library (`snd_lib.c`) and the driver on the PC exactly as the console does for one `select_set(set, id)` call, `tools/bgm_loop.py` finds the loop (the lag with the smallest waveform error: 38,425 ticks for the mode select song, 76,850 for the options / records song, 27,071 / 27,433 for the two select-screen songs; the ending and ceremony music play once), `tools/bgm_enc.c` stores it as 4 bit blocks (28 samples, one of 5 predictors and a scale per block: ~30 dB SNR at 4.3 bits per sample, a loop cross-fade of 50 ms).  Both settings of the stereo option are rendered (`<name>_0.bgm`: two channels, `<name>_1.bgm`: one, the driver plays the same on both sides) and the player switches at the same position when the option changes.  30 MB for six songs.  The library starts a stream where it would send the play command (`select_set`, the id's table value is the key in `data/snd/bgm.idx`), stops it with the first command of a sound set (row 0x17), a driver load, `FUN_06016F24(0)`, and fades it like `FUN_06016F3C(0, vol, time)` (measured on the driver: about 400 / time dB per second after 0.1 s).  Sounds without a stream (menu beeps, jingles of the result screens, the race) still go to the driver.  Decoding costs 0.2 ms per 23 ms block (~1 %).
* **The driver does not tick when it has nothing to do** (`snd.c idle()`): no SCSP voice, no command in the slots or the SH-2's flag, the status bytes of the sound classes (0x780 ..) and the engine words (0x7C0, 0x7E0) are 0.  The 68000's housekeeping (about 500 instructions: the 8 command slots, the 32 voices, the 32 sequencer entries) is skipped; tools/bgm_render.c compares the audio of every song and effect with and without it: identical, except that the *phase* of a few notes in two songs differs, because the driver's internal counters stop while it idles (on the console the phase depends on when the player pressed the button anyway).  With the streams the menus cost ~5 us per tick instead of 447.
* **Hot loops of the driver in C** (`snd.c`, `m68k_hook`): the command slot scan (menus' driver), the 32 sequencer entries of timer B's routine, the 8 tracks and the 8 voices of the main loop (race driver ESDDRVS.DAT) are done in one step while the entries are idle; busy ones run as the driver's code.  Every hook has a verify mode (`snd_core_set_hle_verify`, env `BGM_HLE_VERIFY`): the replaced instructions also run on a copy of the CPU and all registers are compared (abort on a difference); the race with random sound ids (`BGM_RACE=1 BGM_RACE_RANDOM=1 BGM_HLE=1 BGM_HLE_VERIFY=1 BGM_RACE_OUT=file`) and all songs give identical audio with and without.  A race tick went from 484 to 133 dispatches in the synthetic case; PPSSPP: 68000 205 -> 94 us per tick, 329 -> 180 us in total.
* **Mixer**: centred voices need one product per sample, the 8 bit interpolation one multiplication less (identical output: `extracted/snd/golden_sc1.raw`).
* **CD music** (`src/cdda.c`, `tools/conv_cdda.py`): the 16 audio tracks of the disc as 128 kbit/s MP3 (39 MB instead of 431 MB), decoded by the PSP's decoder (`sceMp3`, the Media Engine: no CPU) on a sceAudio channel of its own.  `FUN_0600F756(track, repeat)` starts a track (repeat 15 = for ever), the sound library's `FUN_06016FA4` sets its level (bits 7 .. 5 of the byte = the CD input's level, 6 dB per step below 7), and, like on the console where the drive cannot read data and play audio at once, the next access to a disc file (`sat_load_file` / `sat_load_raw`) ends it.  Race music: tracks 4, 2, 3, 5 for the four stages (`sndev_go`), 6 / 7 the goal / game over jingles, 8 the name entry and ranking, 9 the game over screen, 12 the ending (the code that calls them was ported before).  Development: `data/snddump` also writes `data/cdda.txt` (late blocks and the slowest read of the memory stick).  **Real-PSP findings (26 Oct 2026, from `data/sndlog.txt` on the PSP):** (1) the CD music had never played on the PSP: `sceUtilityLoadAvModule(PSP_AV_MODULE_MP3)` fails there (0x80110f01) and `sceMp3InitResource` then fails (0x8002013a); `cdda.c` now loads the decoder with `sceUtilityLoadModule(PSP_MODULE_AV_AVCODEC / _MP3)` (the call user programs use) and falls back to the other.  (2) The driver's own output was clean in every log: no late block, no clipped sample, peak 76 %, gaps of 23.2 ms.  (3) The memory stick stalls: reads of 42 and 66 ms for 16 KB, more than the music channel's 26 ms of slack; `cdda.c` reads the whole file into memory with a second thread (`loader`, `sceKernelDcacheWritebackRange` for the decoder) and copies from there.  (4) The tracks are encoded for the PSP's speaker (`tools/conv_cdda.py`: low shelf -6 dB below 180 Hz, gain 0.75, peak under 29000 for the MP3 overshoot); `data/cdvol` (percent) and `data/sndvol` (percent) set the music and the driver's level at run time.  **A first attempt failed on the PSP and was removed:** a ring of decoded frames mixed into the driver's output by the sound thread made every screen with music crackle (it was never playing there: the crackle came from the limiter / float path in `snd_psp.c`, which is not understood; PPSSPP did not show it).  Do not change what the audio hardware gets without a PSP test.  The race crackle the user heard before these changes is not explained by the log (the driver's output was clean): the music did not play then, so it came from the driver's sounds or the speaker; with the new build the user thinks it is fixed (not certain).
* **Audio timing log** (`src/sndlog.c`, for the real PSP): an empty `data/sndlog` makes `data/sndlog.txt` (written by a thread of its own, so a slow stick cannot stall the audio): every second the number of blocks, the longest gap between two (a block is 23.2 ms; more than 27 ms = the hardware ran dry = a crackle, also logged as `LATE block` with the time it took to make, the driver tick's maximum, the slots and the game passes per second), the time to make a block, samples that clipped or came within 10 % of it, the peak, the sound library's calls with their time, and from the CD player: the track and level, the decoder's and the stick's slowest times, late music blocks.  An empty `data/nocd` switches the CD music off (to tell the music from the driver's sounds).  `tools/build.sh` puts `sndlog` and `nocd.off` into the dist while `SNDLOG` is not 0.
* Development switches: `data/sndprof` (with `snddump`) counts the 68000's executions per 16 bytes of code (`snd_prof.txt`) and dumps the sound RAM (`snd_ram.bin`); `data/nosnd`.
* **Object sounds** (`src/event.c`, checked by `tools/evvec.py` -> `ev_*_heli.vec` / `ev_0_0_startobj.vec` (format "EVE2": the library calls of every pass, the camera matrix in fixed point, the push the dispatch added to the car) and `tools/test_event.sh`: helicopter 407 + 359 calls, start object 48 calls and 792 push-back passes, **0 differences**).  The helicopter (desert, `FUN_0601DC14` .. `0x0601E228`): id 29 when its flight starts (only in the modes the table at 0x06008C9C allows) and a pan word `0x0200 | angle` every pass of the flight (`FUN_0601E228`: the helicopter's position in the camera's frame, x / z of the camera matrix translated by it, the angle of (-x, z) in 1 / 32 of a half turn, 0 .. 30; behind the camera: far left 0x0200 / right 0x021E).  The start object (arcade, desert; `FUN_0601C370` .. 0x0601C468): a box 6 m wide and 65 m long around the start line keeps the car out (+0x64 / +0x6C of the car get the distance to the nearer edge: this changes the driving) and plays id 2 every 15 passes while it pushes (not on the grid).  `FUN_0601BF80` is only the loader of EVENTTBL.MAD; it has no sound.  play.c sends the calls after the dispatch and flushes after them (the original's order: events, then `start_main`'s flush).
* **The music's fade-out** (`FUN_0601734C` / `FUN_06017360` start, `FUN_06017374` steps once per pass: the CD input's level goes down every `interval` passes through 0xA0 .. 0x20 and ends with 0): the ending's roll uses it (the calls were already in menu_ending.c and went nowhere).  Read from the disassembly, not checked against the original.
* Not ported: the sound sets and events of the 2 player modes (`count_down_start2p`, `result_displaylag`, `vstime_cmp`, driver P2SDDRVS.DAT: its loops have no hooks), the new-best-lap jingle and the last-seconds beep of the race clock.  The replays' sounds (`replay_sdctrl` 0x06016AD4, `count_down_start_replay`) are in `sndev.c`, the title screen's sounds are played by the live driver through `menu_adv.c`, the ending runs on the real replay engine (`src/ending_engine.c`).  Not verified on a real PSP: the CPU numbers above are PPSSPP's virtual time.
